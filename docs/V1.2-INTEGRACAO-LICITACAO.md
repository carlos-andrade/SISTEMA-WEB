# V1.2 — Integração de consulta ao LICITACAO

## Objetivo

Ligar o SISTEMA WEB ao repositório privado `carlos-andrade/LICITACAO` como fonte externa de consulta. O SISTEMA WEB é o único destino de código e documentação deste produto. O LICITACAO permanece estritamente read-only: esta integração não cria, atualiza, elimina nem faz commit no repositório de origem.

## Primeiro caso de uso

A primeira prova de conceito consulta:

- Registo: `ARQUITETURA/exemplos/ufrj-2026-548-oportunidade.json`
- Contrato: `ARQUITETURA/schemas/oportunidade.schema.json`
- Branch de origem: `main`

O backend obtém ambos os ficheiros através da GitHub Contents API, valida o registo com JSON Schema Draft 2020-12 e devolve os dados acompanhados de proveniência.

Endpoint:

`GET /api/integrations/licitation/opportunities/reference`

A resposta contém:
- `data`: registo de oportunidade tal como está na fonte;
- `provenance.repository`, `ref` e `path`: localização da fonte;
- `blob_sha` e `schema_blob_sha`: identificadores Git dos ficheiros;
- `content_sha256`: SHA-256 dos bytes do registo obtido;
- `validation`: resultado da validação estrutural;
- `access_mode`: `read_only`.

## Autorização

Criar um GitHub Fine-grained Personal Access Token com:
- Repository access: apenas `carlos-andrade/LICITACAO`;
- Repository permissions: `Contents: Read-only`;
- sem permissões de escrita.

Não colocar o token no código, no frontend, em commits ou em mensagens. O token é consumido apenas pelo backend.

No diretório raiz do clone SISTEMA-WEB:

```bash
cp .env.example .env
vim .env
```

Preencher `GITHUB_TOKEN` no ficheiro local `.env`. O ficheiro está excluído pelo `.gitignore`. Não enviar o seu conteúdo para o chat nem para o GitHub.

## Configuração e execução

As variáveis são passadas ao contentor backend pelo Docker Compose:
- `GITHUB_TOKEN`
- `LICITACAO_REPOSITORY` (predefinição: `carlos-andrade/LICITACAO`)
- `LICITACAO_REF` (predefinição: `main`)

Depois de configurar o token:

```bash
cd "$HOME/SISTEMA-WEB"
sudo docker compose -f deploy/docker-compose.yml config
sudo docker compose -f deploy/docker-compose.yml up -d --build backend
sudo docker compose -f deploy/docker-compose.yml ps
```

Testar:

```bash
curl --fail http://192.168.60.141:8000/api/health
curl --fail http://192.168.60.141:8000/api/integrations/licitation/opportunities/reference
```

O endpoint também está documentado em `/docs`.

## Respostas de erro

| HTTP | Significado |
|---|---|
| 404 | Ficheiro não encontrado no ref configurado |
| 422 | Registo JSON não cumpre o schema publicado na origem |
| 502 | Falha de acesso à API GitHub, permissões insuficientes ou indisponibilidade |
| 503 | Token não configurado |

Os erros não devem revelar o token nem cabeçalhos de autenticação.

## Limites conhecidos desta entrega

- Caso de referência fixo; ainda não existe pesquisa/listagem de oportunidades.
- Consulta em tempo real à GitHub API; sem cache ou persistência local.
- Validação estrutural pelo schema; não certifica a veracidade material do conteúdo.
- Não há ingestão de anexos PDF, CSV ou XLSX nesta etapa.
- Não há sincronização automática nem webhooks.
- O endpoint devolve os dados originais; não executa normalização adicional.
- A integração não realiza qualquer escrita no LICITACAO.

## Critérios de aceitação

1. Backend consegue autenticar-se no repositório privado com permissão exclusivamente de leitura.
2. Consulta obtém o JSON de referência e o schema da mesma branch configurada.
3. JSON passa na validação Draft 2020-12.
4. Resposta inclui SHA do blob, SHA-256 do conteúdo e localização de origem.
5. Token não aparece no frontend, resposta HTTP, logs ou repositório.
6. Falhas de autenticação e validação são apresentadas sem expor segredos.
7. Repositório LICITACAO permanece sem qualquer alteração provocada pelo SISTEMA WEB.
